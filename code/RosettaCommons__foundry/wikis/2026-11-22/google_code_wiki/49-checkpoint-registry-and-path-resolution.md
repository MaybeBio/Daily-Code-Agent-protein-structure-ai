### Checkpoint Registry and Path Resolution
Checkpoint management within Foundry addresses the need to locate, verify, and register pre-trained models. The system prioritizes flexibility by allowing checkpoint paths to be resolved from multiple sources, including environment variables and user-defined directories. This ensures that models can be easily accessed regardless of their storage location.

The primary mechanism for locating checkpoints involves functions that gather potential directory paths. These functions consider environment variables such as [`FOUNDRY_CHECKPOINT_DIRS`](https://github.com/rosettacommons/foundry/.env#L63) and [`FOUNDRY_CHECKPOINTS_DIR`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L34), along with a default user directory, to establish a comprehensive search order. The [`append_checkpoint_to_env`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L49) utility facilitates persistence by allowing these configured directories to be saved to [`.env`](https://github.com/rosettacommons/foundry/.env#L2) files, streamlining future access.

To simplify the use of known models, Foundry employs a registry system. The [`RegisteredCheckpoint`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L65) dataclass, defined in [`/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py), stores essential metadata for each checkpoint, including its download URL, expected filename, a descriptive text, and an optional SHA256 checksum for integrity verification. A global dictionary, [`REGISTERED_CHECKPOINTS`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L80), maps mnemonic identifiers (e.g., "rfd3na", "proteinmpnn") to these [`RegisteredCheckpoint`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L65) instances. This registry acts as a central catalog, enabling inference engines and other components to refer to specific models by name rather than requiring a direct file path. When a registered checkpoint is requested, its [`get_default_path`](https://github.com/rosettacommons/foundry/src/foundry/inference_engines/checkpoint_registry.py#L71) method attempts to locate the actual file within the established search paths, providing the path to the first existing match or suggesting a default download location if not found. This integration simplifies model loading and ensures consistency across different inference tasks. See [BaseInferenceEngine Architecture and Configuration](#inference-engines-and-model-execution-baseinferenceengine-architecture-and-configuration) for how these checkpoints are utilized by the inference engine.
