### Project and MD Dataset Persistence and Status Tracking
The [`mddb-workflow`](https://github.com/mmb-irb/mddb-workflow/README.md#L4) system uses an SQLite database to manage the lifecycle and status of molecular dynamics (MD) simulation projects and their individual replicas. This database serves as a central registry for all projects and their associated MD runs, tracking their state from initial creation through execution to completion or error.

Project and MD entries are uniquely identified within the database by a Universally Unique Identifier (UUID) and their relative path ([`rel_path`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/mwf.py#L2510)), allowing the system to track them even if their directory locations change. Each entry maintains a [`State`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L33) (e.g., [`NEW`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L35), [`WAITING`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L36), [`RUNNING`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L37), [`ERROR`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L38), [`DONE`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L39)), a descriptive message, and execution identifiers such as [`process_id`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L156) or [`slurm_job_id`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L156) when running.

The database schema, defined and managed by the [`Dataset`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L154) class in [`/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py), includes [`projects`](https://github.com/mmb-irb/mddb-workflow/manual_tools/logger_and_loader.py#L12) and [`mds`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/mwf.py#L1744) tables. The [`mds`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/mwf.py#L1744) table, which stores individual MD replicas, is linked to the [`projects`](https://github.com/mmb-irb/mddb-workflow/manual_tools/logger_and_loader.py#L12) table via a foreign key with an [`ON DELETE CASCADE`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L176) constraint. This ensures that when a project is removed, all its associated MD replicas are automatically deleted from the database, maintaining data integrity. Furthermore, SQLite triggers are employed to automatically update the [`num_mds`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/console.py#L382) count in the [`projects`](https://github.com/mmb-irb/mddb-workflow/manual_tools/logger_and_loader.py#L12) table whenever MD entries are added or removed, preventing discrepancies.

A critical aspect of data integrity, especially in distributed computing environments, is the system's ability to refresh the status of [`RUNNING`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L37) entries. Before any data retrieval or display, the system actively checks if processes or SLURM jobs associated with [`RUNNING`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L37) entries are still active. If a process has terminated or a SLURM job is no longer in the queue, the system automatically updates the entry's state to [`ERROR`](https://github.com/mmb-irb/mddb-workflow/mddb_workflow/core/dataset.py#L38), providing an accurate reflection of the workflow's progress. This proactive status refresh mechanism ensures that the dataset consistently presents reliable information about the ongoing simulations. More details on the concurrency control mechanisms can be found in [Distributed Filesystem Locking for Concurrency](#project-and-md-dataset-management-distributed-filesystem-locking-for-concurrency).
