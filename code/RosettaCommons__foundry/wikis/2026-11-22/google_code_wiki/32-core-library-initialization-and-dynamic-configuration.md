### Core Library Initialization and Dynamic Configuration
The Foundry library performs essential package-wide initialization and configuration to streamline machine learning workflows. This process begins by loading settings from [`.env`](https://github.com/rosettacommons/foundry/.env#L2) files and environment variables, utilizing [`environs`](https://github.com/rosettacommons/foundry/pyproject.toml#L28) within [`/rosettacommons/foundry/src/foundry/__init__.py`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py). This dynamic loading mechanism allows for flexible adjustment of behaviors such as enabling runtime type checking ([`TYPE_CHECK`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L12)), activating debug mode ([`DEBUG`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L13)), performing NaN checks ([`NAN_CHECK`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L14)), and controlling the integration of GPU acceleration components like [`cuequivariance_torch`](https://github.com/rosettacommons/foundry/pyproject.toml#L63).

A key aspect of this initialization is the conditional enablement of runtime type checking through [`beartype`](https://github.com/rosettacommons/foundry/pyproject.toml#L34). If the [`TYPE_CHECK`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L12) environment variable is set, the system calls [`beartype_this_package`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L5) and [`install_import_hook`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L7) to ensure that type annotations are enforced during execution. Similarly, GPU acceleration using [`cuequivariance_torch`](https://github.com/rosettacommons/foundry/pyproject.toml#L63) is conditionally integrated based on the availability of CUDA and a [`DISABLE_CUEQUIVARIANCE`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L35) flag, ensuring that performance-enhancing features are only activated when appropriate. A global [`DISABLE_CHECKPOINTING`](https://github.com/rosettacommons/foundry/src/foundry/__init__.py#L54) flag is also set during this phase, providing a universal control for checkpointing behavior across the library.

Beyond basic settings, Foundry leverages custom Hydra resolvers, defined in [`/rosettacommons/foundry/src/foundry/hydra/resolvers.py`](https://github.com/rosettacommons/foundry/src/foundry/hydra/resolvers.py), for dynamic configuration. The [`resolve_import`](https://github.com/rosettacommons/foundry/src/foundry/hydra/resolvers.py#L28) resolver enables the dynamic loading of Python modules and their attributes directly from configuration files, which is particularly useful for specifying models, datasets, or other components without hardcoding their paths. Another resolver, [`chain_type_info_to_regex`](https://github.com/rosettacommons/foundry/src/foundry/hydra/resolvers.py#L51), dynamically converts [`ChainType`](https://github.com/rosettacommons/foundry/src/foundry/hydra/resolvers.py#L9) or [`ChainTypeInfo`](https://github.com/rosettacommons/foundry/src/foundry/hydra/resolvers.py#L9) enum values into regular expression strings, allowing for flexible filtering and specification of chain types in various structural design tasks. These resolvers allow complex configurations to be specified declaratively in Hydra, with their values resolved dynamically at runtime.
