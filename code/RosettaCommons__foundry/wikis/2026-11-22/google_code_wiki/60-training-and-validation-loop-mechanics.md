### Training and Validation Loop Mechanics
The [`FabricTrainer`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L56) orchestrates the complete training lifecycle, with [`fit`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L329) serving as the primary entry point. This method sets up dataloaders, manages checkpoint loading, performs an initial validation if configured, and iterates through epochs, checking for conditions to stop early.

Within each epoch, the [`train_loop`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L510) is responsible for processing training batches. It incorporates features like gradient accumulation, where gradients are computed over multiple batches before a single optimizer step, allowing for larger effective batch sizes without increased memory consumption. The [`train_loop`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L510) calls the abstract [`training_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L661) method for each batch, which must be implemented by concrete trainers to define the model's forward and backward passes. Following the [`training_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L661), the [`step_optimizer`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L730) method performs the weight updates, including handling NaN/Inf gradient checks and optional gradient clipping. If an Exponential Moving Average (EMA) is configured for the model, [`step_optimizer`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L730) also manages its updates. Concurrently, the [`step_scheduler`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L787) updates the learning rate based on the defined schedule.

The [`validation_loop`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L598) executes periodically to assess model performance on a validation dataset. During this loop, the model is set to evaluation mode to disable operations like dropout, and it iterates through validation batches. For each batch, the abstract [`validation_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L681) method is invoked, which, similar to [`training_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L661), must be implemented by subclasses to perform the forward pass and compute validation metrics. After the validation loop, the model reverts to training mode. Both [`training_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L661) and [`validation_step`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L681) are defined as abstract methods in [`/rosettacommons/foundry/src/foundry/trainers/fabric.py`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py), requiring specific implementations by any trainer extending [`FabricTrainer`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L56).

For a deeper understanding of the trainer's architecture, including how components are constructed and managed, refer to [FabricTrainer: Core Architecture and Lifecycle Management](#training-harness-and-distributed-training-fabrictrainer-core-architecture-and-lifecycle-management) and [Component Construction and Setup](#training-harness-and-distributed-training-component-construction-and-setup). The overall design of the [`FabricTrainer`](https://github.com/rosettacommons/foundry/src/foundry/trainers/fabric.py#L56) is discussed in [Training Harness with PyTorch Lightning Fabric](#foundry-core-library-and-ml-workflows-training-harness-with-pytorch-lightning-fabric).
